# Maintain a project verification skill

A project's `verify-<app>` skill was generated by `create-project-verification-skill`. Its
shipped files (`SKILL.md` and the files the generator's "What you write" marks `unchanged`)
come from the generator, and everything project-specific sits in `PROJECT.md`, the other
`bin/` helpers and `features/`. So an upgrade is mostly a copy, done by a script. Recording
what no recipe covers yet is not part of an upgrade: `/verify-<app> full` does that.

When you need me to make a choice before you can continue, use your question tool if you
have one, or ask in your reply if you don't. If the question gets no answer, ask again in
your reply and wait. Do not answer it yourself.

`<generator>` below is `../create-project-verification-skill/` next to this skill's folder.

## 1. Run the upgrade

From the repository root, on a branch as the repo's conventions say:

```bash
<generator>/references/upgrade
```

With several `verify-*` skills, ask which one and pass its folder. The script copies the
shipped files, converts Markdown recipes into `features/<feature>.sh` scripts, removes the
old runner, recorder and `maintain-verify-<app>` skill, keeps the old files it replaced under
`.cache/upgrade/` (gitignored, so they stay local), and ends with the list of what is left for
you. It is safe to run again. Commit its result before anything else.

## 2. Do what it lists

Do the listed items, in this order, and nothing else. Two items, marked "every upgrade",
are checked even when the script does not list them.

- **`PROJECT.md`**: write it from `.cache/upgrade/SKILL.md` and `.cache/upgrade/README.md`, with
  the sections step 3 of `<generator>/SKILL.md` names. Keep every project fact: isolation,
  launch and cleanup behavior, sign-in, baseline data, helper calls, driving conventions that
  are specific to this project, gotchas. Drop the rules the shipped `SKILL.md` already states
  and everything about the old runner, recorders, contract maps and maintenance modes.
- **`launch.sh` idempotent**: when the run's environment is already up, a second call
  rebuilds and restarts only the app, recreates nothing when the source is unchanged, and
  `doctor.sh` accepts the result. Keep its ownership record and recovery of an interrupted
  launch.
- **The project's stack** (every upgrade): when the repo has an environment
  `<generator>/references/lifecycle.md` would pick as isolated and disposable, such as
  `local-stack/stack`, and `launch.sh` builds its own instead, make `launch.sh` and
  `cleanup.sh` use the stack as `lifecycle.md` says. Start the app in both modes as step 3
  of `<generator>/SKILL.md` says. Delete the code the stack replaces: its own Compose
  project, port picking and source copies.
  Isolation is the stack's job from then on, so a leak found later is fixed in the stack.
  When the stack cannot start something the recipes need, stop and name it.
- **Helper waits and errors** (every upgrade): read each `bin/` helper and make its waits
  and error output follow the "Waits and errors" rules of the new `SKILL.md`, including how
  a helper that restarts the app waits for a real page. Check that a helper that inserts
  rows directly follows the fixture rule in its Data section, against the seed data or the
  dump. `verify lint` checks only recipes, so this is the only check helpers get.
- **Helpers that read the old runner's files**, such as an `observe.sh` reading
  `.cache/drive/<feature>/steps/`: point them at `$VERIFY_DIR/log` and `$EVIDENCE`.
- **`# touches:`**: start subagents (in T3 Code `delegate_task` with `mode: "async"`,
  otherwise your tool's own subagent), each with up to 6 features and this prompt:

  ```
  For each feature recipe below in .agents/skills/verify-<app>/features/, list the source
  files its behavior lives in: the handlers, controllers, components, services, queries and
  migrations it exercises, as repository paths (<app>/<path> in a companion repo). Read the
  recipe, grep for the routes, commands or screens it drives, and follow them into the
  source. Files only, never folders; leave out files every feature only passes through, but
  keep a file that holds this feature's routes or handlers. Write the list on the recipe's
  one '# touches:' line, space-separated, and change nothing else. Run
  .agents/skills/verify-<app>/bin/verify lint <features> and return its last line.
  Features: <feature> <feature> ...
  ```

- **`entrypoints.sh`**, **`actions.sh`**, stale references in helpers, and the
  `## Verification` section of `AGENTS.md` (and `CLAUDE.md`) from
  `<generator>/references/agents-verification.md`.
- Features the script could not convert: run `bin/areas > .cache/areas.txt`, then send
  each area that holds such a feature to a recorder, as the Recorders section of the new
  `SKILL.md` says, after step 3's `bin/verify up`. The recorder keeps the area's existing
  recipes.

## 3. Prove it

Run `bin/verify lint`, then `bin/verify up` twice: the second call must reuse the
environment. When recipes were converted, or a helper or `bin/verify` changed, run
`bin/verify all` once; it moves the run to the production build. Otherwise drive one
feature. Fix the environment yourself when `doctor.sh` stops the run.

Every failing feature is repaired before the PR, also one the upgrade did not break: run
`bin/areas > .cache/areas.txt` when it is missing, and start one recorder for each area
that holds failing features, all at once, with their summary lines. A recorder repairs the
recipe, or marks a product defect `# known failure:`. Then run `bin/verify all` again,
with no `--jobs` (the Done rule in the new `SKILL.md`'s Recipes section says why). Send each
feature that fails there back to a recorder and repeat. Go on only when each of them passes
there or fails at a known failure. Then run `bin/verify uncovered` and `bin/verify down`.

## 4. Ship and report

Commit and open one PR as the repository's conventions say. Report: what the script
changed, what you did from its list, how long `bin/verify all` took, the features the
recorders repaired, and each known failure. When `bin/verify uncovered` listed anything,
end the report with this line, the count filled in: "<n> entry points and actions have no
recipe. Run `/verify-<app> full` to record them."
