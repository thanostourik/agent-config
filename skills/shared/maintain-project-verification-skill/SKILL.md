# Maintain a project verification skill

A project's `verify-<app>` and `maintain-verify-<app>` skills were generated by `create-project-verification-skill`, which keeps improving. This pass updates those skills and their feature map. The three modes match the generated project maintenance skill:

- `/maintain-project-verification-skill`: update the map and drive new and changed steps.
- `/maintain-project-verification-skill map only`: update the map without feature drives.
- `/maintain-project-verification-skill full audit`: update the map and drive every step of every feature.

Honor an equivalent explicit request. Changed helpers get focused live checks in every mode. Map only skips feature drives, not helper validation. The result is at most one PR.

## 1. Locate the target

Find `.agents/skills/verify-*/` and `.agents/skills/maintain-verify-*/` in the repository. Several apps: ask which one. None: stop and point at `/create-project-verification-skill`.

## 2. Read the current generator

Read `create-project-verification-skill`: its `SKILL.md` and everything under its `references/`. It is installed next to this skill (`../create-project-verification-skill/`). That is the spec for what the project's skills should look like.

## 3. Conform

Before editing, record the starting feature map and shared driving conventions for later drive selection. Keep that comparison point across commits in this pass. Compare the project with the spec. First identify its learned setup, isolation, lifecycle, feature prerequisites, ordering, commands and gotchas. Then update the rules without losing that knowledge.

- **Keep:** project-specific behavior and working commands that meet the current spec. Do not regenerate feature knowledge. Do not remove an isolation guard because the generic template does not name it.
- **Bring up to date:** layout, frontmatter and descriptions, required sections and rules, feature shape, the maintenance modes, invocation metadata, Claude Code stubs, `.gitignore`, helpers, deadlines, progress reporting, the driver rule, output paths, evidence links, the `AGENTS.md` and `CLAUDE.md` sections. Merge the maintenance reference with the project's valid adjustments. Do not replace it blindly.
- **Replace obsolete behavior:** fallbacks that name a host browser; Playwright imposed where the project already has its own harness; attaching to services the verification did not create; routine reset-before steps; cleanup that stops resources but keeps their data; concurrent driving of shared state; unbounded waits or a blanket five-minute limit; reports that call failed or incomplete checks passed. Generate project-specific commands for the current lifecycle. An old workaround is not a reason to keep behavior that violates the spec. The ownership rule in `references/lifecycle.md` decides what a run may reuse.
- **Shorten:** where the project's skills restate generator rules at length, cut them down to the project's concrete commands and rules.

When the spec asks for a decision the project never made, such as the isolation level, make it as steps 1 and 2 of the generator describe. Ask the user only what the repo cannot answer.

Reconcile the project's `AGENTS.md` and `CLAUDE.md` using step 6 of the generator and `references/agents-verification.md`. Replace the old one-line instruction with the full section. Merge existing relevant text. Check imported instructions for conflicts. Keep operational commands in the skill. Keep focused test commands and unrelated instructions. Report any older verification system that needs a retirement decision. This is part of an upgrade even when no feature is driven.

## 4. Check and maintain

Exercise changed helpers with the smallest live check that proves them. A cleanup change needs a representative create, use and cleanup cycle, plus a controlled failure after a resource exists. Check that the original environment is restored and evidence survives. A launch or doctor change needs the healthy and failing conditions, including refusal to use a service the verification does not own. A wait-helper change needs short completion and timeout checks. Instruction edits alone need no helper check. These checks use fresh disposable resources and follow the generated Isolation, Drive and Cleanup rules. They do not imply a full audit. Report blocked checks. Do not escalate scope or skip them silently.

Run the conformed `maintain-verify-<app>` with the same mode: **changed recipes** by default, **map only** or **full audit** when explicit. Pass it the starting map and conventions recorded before conformance, so recipes changed during the upgrade are selected. Use its selection rules, which pick steps, not whole files. Do not select features just because generic instructions or helpers were reformatted. Keep conformance edits, helper corrections and map changes in one branch and one PR. If nothing changed, open nothing.

## 5. Report

Say what changed to match the generator, which helper checks ran and their cleanup result, and which mode ran. Follow that mode's Ship report. Keep source-reviewed edits, feature drives and helper checks separate. Helper checks do not prove feature coverage. Unfinished required helper checks make the outcome incomplete even if the map update finished.
