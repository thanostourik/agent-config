# Maintain a project verification skill

A project's `verify-<app>` and `maintain-verify-<app>` skills were generated by `create-project-verification-skill`, which keeps improving. This pass updates those skills and their feature map. The three modes match the generated project maintenance skill:

- `/maintain-project-verification-skill`: update the map and drive new or meaningfully changed recipes.
- `/maintain-project-verification-skill map only`: update the map without feature drives.
- `/maintain-project-verification-skill full audit`: update the map and drive every feature, including unchanged ones.

Honor equivalent explicit source-only or drive-all requests. Changed helpers receive focused live checks in every mode; map only skips feature drives, not helper validation. The result is at most one PR.

## 1. Locate the target

Find `.agents/skills/verify-*/` and `.agents/skills/maintain-verify-*/` in the repository. Several apps → ask which one. None → stop and point at `/create-project-verification-skill`.

## 2. Read the current generator

Read `create-project-verification-skill`: its `SKILL.md` and everything under its `references/`. It is installed next to this skill (`../create-project-verification-skill/` from this skill's folder). That is the spec for what the project's skills should look like.

## 3. Conform

Before conformance edits, record the starting feature map and shared driving conventions for later drive selection; retain this comparison point across commits in the pass. Compare the project against the spec. First identify its learned setup, isolation, lifecycle, feature prerequisites, ordering, commands and gotchas, then update the rules without losing that knowledge:

- **Keep:** project-specific behavior and working commands that meet the current spec. Do not regenerate feature knowledge or remove an isolation guard just because the generic template does not name it.
- **Bring up to date:** layout, frontmatter and descriptions, required sections and rules, feature shape, all three maintenance modes, invocation metadata, Claude Code stubs, `.gitignore`, required helpers, operation deadlines and progress reporting, output paths and evidence links in reports. Merge the maintenance reference with the project's valid adjustments instead of blindly replacing it.
- **Replace obsolete behavior:** attaching to existing services, routine reset-before steps, cleanup that only stops run-owned resources while keeping their data, concurrent driving against shared state, unbounded waits or a blanket five-minute execution limit, and reports that call failed or incomplete checks passed. Generate project-specific commands implementing the generic lifecycle: create a fresh environment for every run, leave pre-existing services and data untouched, remove what the run created, restore what it changed and retain evidence on success or failure. An old workaround is not a reason to preserve behavior that violates the current spec.

When the spec now asks for a decision the project never made (for example, a new section that depends on how the app runs), make it the way steps 1 and 2 of the generator describe, asking the user only what the repo can't answer.

Reconcile the project's `AGENTS.md` verification guidance using step 6 of the generator and its `references/agents-verification.md`. Replace the old one-line instruction with the complete section, merge existing relevant text, and check imported instructions for conflicts. Name the project's actual work scope in `AGENTS.md`; put concrete verification triggers in the skill's description and Pick features section. Replace vague "user-facing work" gates and automatic refactor exemptions with selection based on observable behavior the change could affect. Keep operational commands in the skill, preserve focused test commands and unrelated instructions, and report any older verification system that needs a retirement decision. This is part of an upgrade even when no feature is driven.

## 4. Check and maintain

Exercise changed helpers with the smallest live check that proves their behavior. A cleanup change needs a representative create/use/cleanup cycle and a controlled failure after a resource is created; check the original environment is restored and evidence survives. A launch or doctor change needs the relevant healthy and failing conditions, including refusal to use an existing service. A wait-helper change needs short controlled completion and timeout checks; these do not replace actual feature drives. Instruction edits alone need no helper check, but meaningful recipe changes still require feature drives in the default mode. These checks use fresh disposable resources and follow the generated Isolation, Drive and Cleanup rules; they do not imply a full audit. Report blocked checks without escalating scope or silently skipping them.

Run the conformed `maintain-verify-<app>` with the same requested mode: **changed recipes** by default, **map only** or **full audit** when explicit. Pass the starting map and conventions recorded before conformance, so recipes changed during the upgrade are included in its selection. Use its Select what to drive rules; do not select features merely because generic instructions or helpers were reformatted. Follow its Ship section. Keep conformance edits, helper corrections and map changes in the same branch and PR. If nothing changed, open nothing.

## 5. Report

Say what changed to match the generator, which helper checks actually ran and their cleanup result, and which maintenance mode ran. Follow that mode's Ship report. Distinguish source-reviewed map edits, selected feature drives and helper checks; helper checks do not prove feature coverage. Default mode reports selection reasons and each selected feature's result; map only reports no feature drives; full audit includes every feature's result and omissions. Unfinished required helper checks make the overall maintenance outcome blocked even if the map update finished.
