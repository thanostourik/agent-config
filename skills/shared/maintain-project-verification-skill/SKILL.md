# Maintain a project verification skill

A project's `verify-<app>` and `maintain-verify-<app>` skills were generated by `create-project-verification-skill`, which keeps improving. This pass updates those skills and their feature map. The three modes match the generated project maintenance skill:

- `/maintain-project-verification-skill`: update the map and drive the features with new and changed steps.
- `/maintain-project-verification-skill map only`: update the map without feature drives.
- `/maintain-project-verification-skill full audit`: update the map and drive every feature.

Honor an equivalent explicit request. Changed helpers get focused live checks in every mode. Map only skips feature drives, not helper validation. The result is at most one PR.

When you need me to make a choice before you can continue, use your question tool if you have one, or ask in your reply if you don't. If the question gets no answer, ask again in your reply and wait. Do not answer it yourself.

## 1. Locate the target

Find `.agents/skills/verify-*/` and `.agents/skills/maintain-verify-*/` in the repository. Several apps: ask which one. None: stop and point at `/create-project-verification-skill`.

## 2. Read the current generator

Read `create-project-verification-skill`: its `SKILL.md` and everything under its `references/` except `drive.sh`, `steps.sh` and `rec.sh`, which the project gets as copies without your reading them. It is installed next to this skill (`../create-project-verification-skill/`). That is the spec for what the project's skills should look like.

From the project, read `verify-<app>/SKILL.md`, `features/README.md` and one feature file as a sample of the recipe format, in one command that also copies `features/README.md` to `.agents/skills/verify-<app>/.cache/starting-README.md` and prints `maintain-verify-<app>/SKILL.md` only as one `diff` against the generator's `maintain-verify.md` with `<app>` and `<driver>` filled in. That diff is your read of the project's maintenance skill: you read the generator's copy or the project's, never both. Never read every feature file: recipes are not part of this pass.

## 3. Conform

That copy, made before any edit, records the starting feature map and shared driving conventions for later drive selection. Keep it across commits in this pass. Compare the project with the spec. First identify its learned setup, isolation, lifecycle, driving conventions, commands and gotchas. Then update the rules without losing that knowledge.

- **Keep:** project-specific behavior and working commands that meet the current spec. Do not regenerate feature knowledge. Do not remove an isolation guard because the generic template does not name it.
- **Bring up to date:** layout, frontmatter and descriptions, required sections and rules, the feature file shape and driving conventions in `features/README.md`, `bin/drive.sh`, `bin/steps.sh` and `bin/rec.sh` (copied from the generator with `cp`, then `git diff --stat` of them names the changed ones step 4 checks; read no diff of them), helpers keyed on `VERIFY_SESSION`, one real example call on every line of the Helpers section, the maintenance modes, the recorder and fixer briefs as templates with `{{...}}` placeholders, the Brief files commands that fill them, one-line prompts and results, report files, invocation metadata, Claude Code stubs, `Bash(sudo:*)` in `permissions.deny` of `.claude/settings.json` (merged in when missing), `.gitignore`, helpers, deadlines, the progress-line rule, the driver rule, output paths, evidence links, the `AGENTS.md` and `CLAUDE.md` sections. Merge the maintenance reference with the project's valid adjustments, which the step 2 diff shows. Do not replace it blindly. Shell code the reference now runs through `bin/rec.sh` is no adjustment: the copied `rec.sh` replaces it. The merged maintenance skill states `Recorders at once` in Update the map step 3: a project skill without that value gets 6, and one that has a value keeps it.
- **Replace obsolete behavior:** fallbacks that name a host browser or fall back to a host tool; driver blocks that claim precedence over the host instead of stating the user's explicit request; Playwright imposed where the project already has its own harness; attaching to services the verification did not create; routine reset-before steps; cleanup that stops resources but keeps their data; concurrent driving of shared state; unbounded waits or a blanket five-minute limit; reports that call failed or incomplete checks passed. Generate project-specific commands for the current lifecycle. An old workaround is not a reason to keep behavior that violates the spec. The ownership rule in `references/lifecycle.md` decides what a run may reuse.
- **Leave recipes to step 4:** conformance edits no recipe. After copying the runner, run `bin/drive.sh --check` to learn which recipes it refuses, and in the same call list the feature files without a `## Contract` section with `grep -L '^## Contract$'` over `features/*.md` except `README.md`. Add those to the refused list: once `maintain-verify-<app>` writes its contract map, `drive.sh --check` refuses a file without one for every feature the map names, so the first pass after this change converts them, and each converted file counts as changed in the record step. In modes that drive, those features are selected and go to recorders for conversion. Map only reports them, and `drive.sh` refuses them until a pass that drives converts them. When `verify-<app>`'s Isolation section says `checks-only`, skip `bin/drive.sh --check` and the `drive.sh`, `steps.sh` and `rec.sh` checks in step 4, and report them skipped because recipes there have no `bash` blocks and nothing is driven.
- **Shorten:** where the project's skills restate generator rules at length, cut them down to the project's concrete commands and rules.

When the spec asks for a decision the project never made, such as the isolation level, make it as steps 1 and 2 of the generator describe. Ask the user only what the repo cannot answer.

Reconcile the project's `AGENTS.md` and `CLAUDE.md` using step 6 of the generator and `references/agents-verification.md`. Replace the old one-line instruction with the full section. Merge existing relevant text. Check imported instructions for conflicts. Keep operational commands in the skill. Keep focused test commands and unrelated instructions. Report any older verification system that needs a retirement decision. This is part of an upgrade even when no feature is driven.

## 4. Check and maintain

Exercise changed helpers with the smallest live check that proves them. A changed `drive.sh` or `steps.sh` needs one existing feature driven with `bin/drive.sh`; if no recipe has `bash` blocks yet, have one converted first by a recorder started through the brief files of `maintain-verify-<app>`'s Update the map step 3. A new or changed `rec.sh` needs one run with the app launched: stage an existing feature that `bin/drive.sh --check` accepts with `bin/rec.sh <feature> start`, run it with `bin/rec.sh <feature> run` and see it pass, then remove its `.cache/record/<feature>/` folder without installing. When no recipe passes `bin/drive.sh --check`, have a recorder convert one first, as for `drive.sh`, and install it with `bin/rec.sh install` instead of removing it, so it also serves as the example recipe. A cleanup change needs a representative create, use and cleanup cycle, plus a controlled failure after a resource exists. Check that the original environment is restored and evidence survives. A launch or doctor change needs the healthy and failing conditions, including refusal to use a service the verification does not own. A wait-helper change needs short completion and timeout checks. Instruction edits alone need no helper check. These checks use fresh disposable resources and follow the generated Isolation, Drive and Cleanup rules. They do not imply a full audit. Report blocked checks. Do not escalate scope or skip them silently.

Run the conformed `maintain-verify-<app>`, without reading it again, from the generator's `maintain-verify.md` and the adjustments you kept, with the same mode: **changed recipes** by default, **map only** or **full audit** when explicit. Pass it the starting record in `.cache/starting-README.md` and the features `bin/drive.sh --check` refused, so changes made during the upgrade and the refused recipes are selected. Before the first run that brings `features/last-reviewed`, rewrite each `## Change triggers` line that has no backticked path glob, or a glob holding `[(]`, `[)]`, `[[]` or `\`, into the generator's shape with literal paths, `` `<glob>`, `<glob>`: <feature>, <feature> ``, from the source it names. That run finds no `last-reviewed`, so it records every feature as before, and its Ship writes the file. Use its selection rules. Do not select features just because generic instructions or helpers were reformatted. Keep conformance edits, helper corrections and map changes in one branch and one PR. If nothing changed, open nothing.

## 5. Report

Say what changed to match the generator, which helper checks ran and their cleanup result, and which mode ran. Follow that mode's Ship report. Keep source-reviewed edits, feature drives and helper checks separate. Helper checks do not prove feature coverage. When you break something on purpose to test a helper and the helper correctly stops, write "stopped it, as expected", not "failed". Example: "Doctor: I stopped a container, and Doctor correctly refused to continue." Unfinished required helper checks make the outcome incomplete even if the map update finished.
