# Maintain a project verification skill

A project's `verify-<app>` and `maintain-verify-<app>` skills were generated by `create-project-verification-skill`, which keeps improving. This pass updates those skills and their feature map. The three modes match the generated project maintenance skill:

- `/maintain-project-verification-skill`: update the map and drive the features with new and changed steps.
- `/maintain-project-verification-skill map only`: update the map without feature drives.
- `/maintain-project-verification-skill full audit`: update the map and drive every feature.

Honor an equivalent explicit request. Changed helpers get focused live checks in every mode. Map only skips feature drives, not helper validation. The result is at most one PR.

When you need me to make a choice before you can continue, use your question tool if you have one, or ask in your reply if you don't. If the question gets no answer, ask again in your reply and wait. Do not answer it yourself.

## 1. Locate the target

Find `.agents/skills/verify-*/` and `.agents/skills/maintain-verify-*/` in the repository. Several apps: ask which one. None: stop and point at `/create-project-verification-skill`.

## 2. Read the current generator

One helper agent, the **conformer**, does steps 2 and 3, because your memory must stay small for the recording that step 4 starts. Render its brief and start it with the command and prompt under Conformer brief, at the end of step 3, then read only the line it returns. On `blocked: <question>`, ask the user, append `Answer: <answer>` to the brief file and start a new conformer. Without a subagent tool, do steps 2 and 3 yourself. Then go to step 4.

The conformer reads `create-project-verification-skill`: its `SKILL.md` and everything under its `references/` except `drive.sh`, `steps.sh` and `rec.sh`, which the project gets as copies without your reading them. It is installed next to this skill (`../create-project-verification-skill/`). That is the spec for what the project's skills should look like.

From the project, read `verify-<app>/SKILL.md`, `features/README.md` and one feature file as a sample of the recipe format, in one command that also copies `features/README.md` to `.agents/skills/verify-<app>/.cache/starting-README.md` and prints `maintain-verify-<app>/SKILL.md` only as one `diff` against the generator's `maintain-verify.md` with `<app>` and `<driver>` filled in. That diff is your read of the project's maintenance skill: you read the generator's copy or the project's, never both. Never read every feature file: recipes are not part of this pass.

## 3. Conform

That copy, made before any edit, records the starting feature map and shared driving conventions for later drive selection. Keep it across commits in this pass. Compare the project with the spec. First identify its learned setup, isolation, lifecycle, driving conventions, commands and gotchas. Then update the rules without losing that knowledge.

- **Keep:** project-specific behavior and working commands that meet the current spec. Do not regenerate feature knowledge. Do not remove an isolation guard because the generic template does not name it.
- **Bring up to date:** layout, frontmatter and descriptions, required sections and rules, the feature file shape and driving conventions in `features/README.md`, `bin/drive.sh`, `bin/steps.sh` and `bin/rec.sh` (copied from the generator with `cp`, then `git diff --stat` of them names the changed ones step 4 checks; read no diff of them), helpers keyed on `VERIFY_SESSION`, `bin/observe.sh` and `bin/find.sh` (written from the peek command in `maintain-verify-<app>`'s Brief files when it has one), a `launch.sh` record of pre-existing resources that leaves out other `verify-<app>` projects' resources (conformed when it does not, and reported in one sentence), one real example call on every line of the Helpers section, the maintenance modes, the recorder and fixer briefs as templates with `{{...}}` placeholders, the Brief files commands that fill them, one-line prompts and results, report files, invocation metadata, Claude Code stubs, `Bash(sudo:*)` in `permissions.deny` of `.claude/settings.json` (merged in when missing), `.gitignore`, helpers, deadlines, the progress-line rule, the driver rule, output paths, evidence links, the `AGENTS.md` and `CLAUDE.md` sections. Merge the maintenance reference with the project's valid adjustments, which the step 2 diff shows. Do not replace it blindly. Shell code the reference now runs through `bin/rec.sh` is no adjustment: the copied `rec.sh` replaces it. The merged maintenance skill states `Recorders at once` in Update the map step 3: a project skill without that value gets 6, and one that has a value keeps it.
- **Replace obsolete behavior:** fallbacks that name a host browser or fall back to a host tool; driver blocks that claim precedence over the host instead of stating the user's explicit request; Playwright imposed where the project already has its own harness; attaching to services the verification did not create; routine reset-before steps; cleanup that stops resources but keeps their data; concurrent driving of shared state; unbounded waits or a blanket five-minute limit; reports that call failed or incomplete checks passed; a `## Change triggers` section in `features/README.md` and selection by its path globs, deleted: features are picked from what a change touches. Generate project-specific commands for the current lifecycle. An old workaround is not a reason to keep behavior that violates the spec. The ownership rule in `references/lifecycle.md` decides what a run may reuse.
- **Leave recipes to step 4:** conformance edits no recipe. After copying the runner, run `bin/drive.sh --check` to learn which recipes it refuses, and in the same call list the feature files without a `## Contract` section with `grep -L '^## Contract$'` over `features/*.md` except `README.md`. Add those to the refused list: once `maintain-verify-<app>` writes its contract map, `drive.sh --check` refuses a file without one for every feature the map names, so the first pass after this change converts them: it adds the `bash` blocks and Contract lines `drive.sh --check` asks for. Each converted file counts as changed in the record step. In modes that drive, those features are selected and go to recorders for conversion. Map only reports them, and `drive.sh` refuses them until a pass that drives converts them. When `verify-<app>`'s Isolation section says `checks-only`, skip `bin/drive.sh --check` and the `drive.sh`, `steps.sh` and `rec.sh` checks in step 4, and report them skipped because recipes there have no `bash` blocks and nothing is driven.
- **Shorten:** where the project's skills restate generator rules at length, cut them down to the project's concrete commands and rules.

When the spec asks for a decision the project never made, such as the isolation level, make it as steps 1 and 2 of the generator describe. Ask the user only what the repo cannot answer.

Reconcile the project's `AGENTS.md` and `CLAUDE.md` using step 6 of the generator and `references/agents-verification.md`. Replace the old one-line instruction with the full section. Merge existing relevant text. Check imported instructions for conflicts. Keep operational commands in the skill. Keep focused test commands and unrelated instructions. Report any older verification system that needs a retirement decision. This is part of an upgrade even when no feature is driven.

### Conformer brief

```
You are the conformer for verify-{{app}}: you bring the project's verification skills up to the current generator. Another agent runs the checks and the maintenance pass after you.

Repository root: {{root}}; run every command from there. The generator is {{generator}}. Read steps 2 and 3 of {{skill}}, and nothing else of that file, and do them for .agents/skills/verify-{{app}} and .agents/skills/maintain-verify-{{app}}.
Ask the user nothing: return blocked with the question instead. Launch nothing, edit no recipe, and do not commit or push.
Copy the generator's driving conventions and add none of your own: a project-specific convention is a Gotcha, written by a recorder or fixer that hit it, never by conformance.
Write the features step 3 adds to the refused list, space-separated, to .agents/skills/verify-{{app}}/.cache/refused.txt. Write what the report needs, such as decisions made, a conformed launch.sh and older verification systems, to .agents/skills/verify-{{app}}/.cache/conform-report.md. Use one Bash call for each.

Then return only one of these lines:
conformed: <files changed>; runner files copied: <yes when cp changed drive.sh, steps.sh or rec.sh, else no>; helpers added: <names or none>
nothing to change
blocked: <reason>
```

Render it from the repository root in one command, with `<skill>` the folder of this `SKILL.md` and `<app>` the target's name:

```
s=<skill>; v=.agents/skills/verify-<app>; mkdir -p $v/.cache
awk '$0 == "### Conformer brief" {s = 1; next} s && /^```/ {if (f) exit; f = 1; next} f' $s/SKILL.md | sed -e "s|{{root}}|$PWD|g" -e "s|{{app}}|<app>|g" -e "s|{{skill}}|$s/SKILL.md|g" -e "s|{{generator}}|$s/../create-project-verification-skill|g" > $v/.cache/conform-brief.md
```

The whole prompt of the conformer:

```
You are the conformer for verify-<app>. Read <repository root>/.agents/skills/verify-<app>/.cache/conform-brief.md and do what it says.
```

## 4. Check and maintain

The conformer's line names the changed files. Exercise changed helpers with the smallest live check that proves them. A changed `drive.sh` or `steps.sh` needs one existing feature driven with `bin/drive.sh`; if no recipe has `bash` blocks yet, have one converted first by a recorder started through the brief files of `maintain-verify-<app>`'s Update the map step 3. A new or changed `rec.sh` needs one run with the app launched: stage an existing feature that `bin/drive.sh --check` accepts with `bin/rec.sh <feature> start`, run it with `bin/rec.sh <feature> run` and see it pass, then remove its `.cache/record/<feature>/` folder without installing. When no recipe passes `bin/drive.sh --check`, have a recorder convert one first, as for `drive.sh`, and install it with `bin/rec.sh install` instead of removing it, so it also serves as the example recipe; skip this when a full audit follows, since its first recorder and drive cover it. A cleanup change needs a representative create, use and cleanup cycle, plus a controlled failure after a resource exists. Check that the original environment is restored and evidence survives. A launch or doctor change needs the healthy and failing conditions, including refusal to use a service the verification does not own. A wait-helper change needs short completion and timeout checks. Instruction edits alone need no helper check. These checks use fresh disposable resources and follow the generated Isolation, Drive and Cleanup rules. They do not imply a full audit. Report blocked checks. Do not escalate scope or skip them silently.

Read the conformed `maintain-verify-<app>/SKILL.md` once and run it with the same mode: **changed recipes** by default, **map only** or **full audit** when explicit. Pass it the starting record in `.cache/starting-README.md` and the refused features in `.cache/refused.txt`, in every mode; a full audit converts them like any other, so changes made during the upgrade and the refused recipes are selected. A run that finds no `features/last-reviewed` records every feature, and its Ship writes the file. Use its selection rules. Do not select features just because generic instructions or helpers were reformatted. Keep conformance edits, helper corrections and map changes in one branch and one PR. If nothing changed, open nothing.

## 5. Report

Say what changed to match the generator, from the conformer's line and one read of `.cache/conform-report.md`, which helper checks ran and their cleanup result, and which mode ran. Follow that mode's Ship report. Keep source-reviewed edits, feature drives and helper checks separate. Helper checks do not prove feature coverage. Word a helper check that broke something on purpose as step 8 of the generator says. Unfinished required helper checks make the outcome incomplete even if the map update finished.
