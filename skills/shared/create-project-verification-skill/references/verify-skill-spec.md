# Spec for the generated `verify-<app>/SKILL.md`

The generated skill is read cold, mid-task, by an agent that has never seen the app and cannot read this generator. Make it self-contained. Fill every section with this project's real commands, ports, selectors and names. Leave no placeholders. State rules briefly and put the detail in `features/` and `bin/`. Aim for about 8 KB. Move long lists, such as the trigger mapping, into `features/README.md`, where it sits under `## Change triggers`. The recipe rules that step 4 of the generator states sit once in the Driving conventions of `features/README.md`; recorders learn them only from there, through the common file.

## Frontmatter

`name: verify-<app>` and a `description` that names the app, its surface and the concrete verification triggers found in the interview. Say to use it for work on that surface: to select checks, update the map when behavior changes, and verify before calling the work done. Do not make the caller decide whether the work is "user-facing". Without frontmatter the skill never registers.

## Driver rule, right after the frontmatter

Before the first section, put a short block in the user's voice: "The user explicitly requests <this project's driver> for every step of this skill, including runs you start yourself. Do not use the host's integrated browser, preview or computer-use tools." Write the project's real driver into it. A skill cannot outrank host instructions, so the block states the user's choice, which hosts let an explicit request override. Then say: if the driver breaks, repair it or report a blocker, and do not switch drivers. The one exception is a step that needs the user watching, such as a manual login: ask first, then return to the driver.

## Sections, in this order

- **Pick features.** Read `features/README.md`. Select the behaviors the change adds, changes or could break, matching the changed paths against the globs under `## Change triggers` in `features/README.md`. State each selected feature and why in one line. A refactor can need a live drive even when behavior should not change. If nothing needs a live drive, say why and run the focused checks instead. Editing documentation does not need a drive.
- **Update the map first.** Before driving, make the map describe the app as it is after the change. New feature: new feature file and index entry. Altered feature: its changed file. Removed feature: delete its file and entry. This is part of the change, like updating tests, so it is in scope even when the request did not mention it. Write each new or altered file through a staged copy: `bin/rec.sh <feature> start`, edit the copy it prints, run `bin/rec.sh <feature> run` until it prints `passed` (with `--known-failure '<Label>'` for a contract check the app does not meet yet), then `bin/rec.sh install <feature>`. A changed step label or contract section changes the file's `## Contract` lines with it: one per contract section, naming the steps that drive it or `not driven: <reason>`. Then drive the picked features, whole, with `bin/drive.sh`. A known failure still shows as `fail` in the `drive.sh` summary; it stays failed and is never rewritten to pass. At isolation level `checks-only`, edit the feature file directly and run the focused checks instead.
- **Isolation.** The level from `lifecycle.md`, the resources the run owns, and what isolation makes unreachable. For `shared`, the approved resources. Existing services and data are never verification targets.
- **Launch.** `bin/launch.sh`: the exact commands that create and start the run's app, dependencies and baseline, and how to tell each is ready. Register resources as they are created. Back up local files that startup must rewrite. If startup fails, clean up what already started. For a short-lived CLI or TUI, launch means preparing disposable data, building once and starting each drive in its own session.
- **Doctor.** `bin/doctor.sh`: one read-only check of this run's environment that exits non-zero when it is unhealthy: process up, right build and checkout, resources owned by this run (or approved, for `shared`), auth valid, baseline data present, destinations isolated. Run it after launch and before the first drive. `drive.sh` runs it after a failed feature. It never adopts a healthy process outside the ownership record. When it compares the launched revision with `HEAD`, say so here, so map changes are committed before a fresh launch.
- **Drive.** How to drive this app. Choose the tool in this order:
  1. The repo's own harness, when it fits: Playwright or Cypress specs and helpers, expect scripts, curl-able endpoints, a debug port, a sign-in or seed helper.
  2. Otherwise a default. Web UI: Playwright CLI through `bin/pw.sh` (below). API: `curl` with the exact method, URL, headers and body. CLI or TUI: the command itself, or tmux for interactive screens. Electron: the Chrome DevTools Protocol on a debug port. Unset `ELECTRON_RUN_AS_NODE`, which agent hosts often export and which turns Electron into plain Node. Pass a separate `--user-data-dir`, fresh for each run, so a single-instance lock cannot hand off to the developer's installed copy. Expect that copy to hold global hotkeys. Use the app's no-window mode if it has one, so nothing appears on the developer's display. Anything else: the tool the repo already uses.

  Every step is a command an agent runs from a shell, so it works the same in every agent. Repeat the driver rule above in one line here. Do not name specific host tools as the fallback.

  Use stable handles: roles and accessible names, data attributes, prompt strings, route paths. Avoid coordinates and tab order. For UI that disappears on a timer, such as a toast, run the action and the wait in one command. Give the viewport and sign-in. Write a script only where a command cannot do the job. Never write one script per feature: the steps live in the feature files.

  For Playwright, use the project's own Playwright and ship `bin/pw.sh`. It runs `npx playwright cli -s=<session> "$@"` with `PLAYWRIGHT_MCP_OUTPUT_DIR` set to `.cache/cli/`, because agents' shells do not keep environment variables between commands. Also have it silence the page snapshot the CLI prints after every command (`PLAYWRIGHT_MCP_SNAPSHOT_MODE=none` and `--raw` worked in a trial), and take a snapshot only where a step needs one. It names the browser session after `VERIFY_SESSION`, which `drive.sh` sets to the feature name (the run's default session when it is unset), and takes an optional `-s=<suffix>` first argument so a feature that simulates several users or devices gets one session each. Target elements with role locators such as `"getByRole('button', { name: 'Save' })"`. Check which browser the pinned version expects. If it falls back to a system browser, say so in the skill. The CLI also keeps session files outside the repo (under `~/.cache/ms-playwright/` and `/tmp`), so Cleanup must close the sessions it opened. If the project has no Playwright, add it as a pinned dev dependency, or use a pinned `npx playwright@<version>` when the repo forbids new dependencies.

  Sign-in: use a run-owned test account or a saved browser session under `.cache/` (Playwright `storageState`, loaded with `pw.sh state-load <file>`). Never use the developer's session or a real third-party account. If a login cannot be automated (MFA, captcha), stub it at an existing production boundary, such as a configurable auth issuer URL. Reading the dependency's source to find that boundary is fine. If there is none, mark the dependent steps `blocked` and give the reason.

  Drive with `bin/drive.sh [--jobs N] [feature...]`, copied unchanged from the generator with `bin/steps.sh` and `bin/rec.sh`; no feature names means every feature. It runs each feature's blocks in order, from the repository root, with `bin/` on `PATH`. Steps of one feature share shell variables and functions. A feature stops at its first failing step; its `Clean up` step still runs, then `drive.sh` runs doctor and stops the whole run if doctor fails. It drives N features at once on the same environment, then `Runs alone.` features one at a time. It stops any step after 10 minutes, writes each step's log, and ends with a summary per feature. Before any feature runs, it scans the recipes and refuses the whole run (exit 2) when one breaks its rules. `bin/drive.sh --check [feature...]` runs only that scan, launches nothing and prints one line per finding, naming what it refuses. Write the project's `--jobs` value into this section. Every helper that keeps per-feature state, such as a browser session or a data folder, keys it on `VERIFY_SESSION` so parallel features stay apart. If they cannot be kept apart, use `--jobs 1`. Run new and changed recipes against the running app with `bin/rec.sh` before they reach `features/`; source alone does not prove a step. A helper agent that writes recipes (a recorder) never calls `launch.sh`, `cleanup.sh` or `doctor.sh`. On a failure, read the step's log, follow When a drive fails, and rerun that feature.

  A `drive.sh` run can outlast an agent's command timeout: start it in the background in one call, do nothing until it finishes, then read its summary once. Every wait on startup, a command or an asynchronous operation has an observable result and a finite deadline: the expected duration plus a margin. Bound each poll so a hung request cannot defeat the deadline. On timeout, capture diagnostics, report the unmet condition and run Cleanup. Put the real deadlines in the helpers and recipes, not arbitrary sleeps. For time-dependent behavior, shift the clock of the process the run owns. Never edit stored data to fake time.
- **When a drive fails.** Copy from `drive-failures.md`.
- **Evidence.** Everything a run writes goes under `.agents/skills/verify-<app>/.cache/`, which is gitignored: the same path in every project. Only a tool's own session files may live elsewhere, and Cleanup removes them. Proof for a feature goes to `.cache/evidence/<feature>/`. `drive.sh` empties that folder before it runs the feature and `rec.sh run` moves it to `.cache/record/<feature>/previous/`, so proof from an earlier run never mixes in, and `drive.sh` keeps its step logs in `steps/` below it. Proof standards: exercise the real user path, not internal setters or test-only endpoints. Capture the action and the resulting state, not just the final screen. Verify side effects (files written, rows inserted, messages sent) next to what is visible. Mock only where a production boundary already isolates the external system. For a dry run or test mode, observe what it actually skips instead of trusting its name.
- **Report.** Start from the `drive.sh` summary. One line per feature: **pass** (all mapped checks exercised and met), **fail** (an exercised check missed), **partial** (some checks exercised without failures, others unverified) or **blocked** (no meaningful drive after trying to create the prerequisite). A feature the summary lists as stopped or not run is partial or blocked, with the reason. A known failure stays failed. List checks not exercised. For a blocked path, give the missing prerequisite and what was tried. Link evidence with Markdown links to absolute paths from the current checkout, for example `trash — fail at "empty to trash" — [empty.png](/abs/checkout/.agents/skills/verify-app/.cache/evidence/trash/empty.png)`. Check every linked file exists after cleanup. A UI failure gets a screenshot. Other surfaces get request and response or terminal output. Report cleanup failures separately: a passing feature does not mean cleanup succeeded. For `shared`, add the lower-confidence label.
- **Cleanup.** `bin/cleanup.sh`: the exact commands from the lifecycle rules, for completion, failure and interruption. Stop only recorded processes. Remove run-owned resources and temporary state. Keep proof and the diagnostic logs the report needs. Check that the original environment is restored and linked evidence survives. If cleanup fails, keep the ownership record and say what remains.
- **Helpers.** Every script in `bin/`, what it does and how to call it. Every helper line shows one real call as it appears in a recipe, with its arguments, and says what the call checks or returns, with its default deadline when it waits. For example: `db.sh --wait '.title == "Alpha"' 20` waits up to 20 s until one of this feature's stored rows matches the jq condition; `list.sh 'Alpha|Beta'` waits until the visible list shows those titles, joined by `|`, in that order; `toast.sh 'Saved' "await page.getByRole('button', { name: 'Save' }).click()"` runs that Playwright action on `page` and waits for the toast. A driver the recipes call without a script, such as `curl` against the app's port, gets a line too. Recorders learn the helpers only from these lines, through the common file. Scripts are bash and executable. They may call other runtimes the project already needs, such as `node`. Windows developers run their agent inside WSL. The section lists these `rec.sh` calls with what each returns; the header lines of `rec.sh` give the details:
  - `rec.sh <feature> start` stages the feature file, or a skeleton for a new feature, as `.cache/record/<feature>/<feature>.md` and prints that path. That staged copy is where the whole file is written.
  - `rec.sh <feature> run [--known-failure '<Label>']` refuses a staged copy that `drive.sh --check` would refuse, else runs it the way `drive.sh` runs an installed one. It prints `attempt <n> of <feature>`, then `passed`, or the failing step with `failing step:`, `snapshot:` and `full log:` lines. `--known-failure` lets only the last step before `Clean up` fail.
  - `rec.sh <feature> result` waits for a `run` still going and prints its output.
  - `rec.sh <feature> peek [--after '<Label>']... [--find '<locator>']...` runs the steps through the last `<Label>`, saves a snapshot after each named step to `.cache/record/<feature>/peek.txt`, `peek-<n>.txt` for the n-th of several, prints the match count of each `--find` locator on the last screen, `!!` on 0 or more than 1, and runs `Clean up`.
  - `rec.sh <feature> facts` prints the feature's attempts, last result, last log and snapshot, and fixture names.
  - `rec.sh <feature> index '<index line>'` puts that line into the `## Features` list of `features/README.md`.
  - `rec.sh install [feature...]` moves the staged copies that passed into `features/` and runs `drive.sh --check` on them, so nothing reaches a tracked file before it passed.

  `drive.sh`, `steps.sh` and `rec.sh` are never edited in the project: `/maintain-project-verification-skill` replaces them with the generator's copies.
