# Spec for the generated `verify-<app>/SKILL.md`

The generated skill is read cold, mid-task, by an agent that has never seen the app and cannot read this generator. Make it self-contained. Fill every section with this project's real commands, ports, selectors and names. Leave no placeholders. State rules briefly and put the detail in `features/` and `bin/`. Aim for about 8 KB. Move long lists, such as a per-file trigger mapping, into `features/README.md`.

## Frontmatter

`name: verify-<app>` and a `description` that names the app, its surface and the concrete verification triggers found in the interview. Say to use it for work on that surface: to select checks, update the map when behavior changes, and verify before calling the work done. Do not make the caller decide whether the work is "user-facing". Without frontmatter the skill never registers.

## Driver rule, right after the frontmatter

Before the first section, put a short block that names this project's driver and says: use it for every step. Do not reach for the host's integrated browser, preview or computer-use tools first, even when the host instructs agents to prefer them. This skill's order takes precedence for the whole run, including runs an agent started on its own. Fall back to a host tool only for a step the driver cannot do, after trying to fix the step or the driver. Say why in the report, and return to the driver for the next step.

## Sections, in this order

- **Pick features.** Read `features/README.md`. Select the behaviors the change adds, changes or could break, using this project's triggers. State each selected feature and why in one line. A refactor can need a live drive even when behavior should not change. If nothing needs a live drive, say why and run the focused checks instead. Editing documentation does not need a drive.
- **Update the map first.** Before driving, make the map describe the app as it is after the change. New feature: new feature file and index entry. Altered feature: edit its file. Removed feature: delete its file and entry. This is part of the change, like updating tests, so it is in scope even when the request did not mention it. Then drive each picked feature file once, whole.
- **Isolation.** The level from `lifecycle.md`, the resources the run owns, and what isolation makes unreachable. For `shared`, the approved resources. Existing services and data are never verification targets.
- **Launch.** The exact commands that create and start the run's app, dependencies and baseline, and how to tell each is ready. Register resources as they are created. Back up local files that startup must rewrite. If startup fails, clean up what already started. For a short-lived CLI or TUI, launch means preparing disposable data, building once and starting each drive in its own session.
- **Doctor.** One read-only check of this run's environment: process up, right build and checkout, resources owned by this run (or approved, for `shared`), auth valid, baseline data present, destinations isolated. Run it after launch, before the first drive and after a failed drive. It never adopts a healthy process outside the ownership record.
- **Drive.** How to drive this app. Choose the tool in this order:
  1. The repo's own harness, when it fits: Playwright or Cypress specs and helpers, expect scripts, curl-able endpoints, a debug port, a sign-in or seed helper.
  2. Otherwise a default. Web UI: Playwright CLI through `bin/pw.sh` (below). API: `curl` with the exact method, URL, headers and body. CLI or TUI: the command itself, or tmux for interactive screens. Electron: the Chrome DevTools Protocol on a debug port. Unset `ELECTRON_RUN_AS_NODE`, which agent hosts often export and which turns Electron into plain Node. Pass a separate `--user-data-dir`, fresh for each run, so a single-instance lock cannot hand off to the developer's installed copy. Expect that copy to hold global hotkeys. Use the app's no-window mode if it has one, so nothing appears on the developer's display. Anything else: the tool the repo already uses.

  Every step is a command an agent runs from a shell, so it works the same in every agent. Repeat the driver rule above in one line here. Do not name specific host tools as the fallback.

  Use stable handles: roles and accessible names, data attributes, prompt strings, route paths. Avoid coordinates and tab order. For UI that disappears on a timer, such as a toast, run the action and the wait in one command. Give the session name, viewport and sign-in. Write a script only where a command cannot do the job. Never write one script per feature: the steps live in the feature files.

  For Playwright, use the project's own Playwright and ship `bin/pw.sh`. It runs `npx playwright cli -s=<app> "$@"` with `PLAYWRIGHT_MCP_OUTPUT_DIR` set to `.cache/cli/`, because agents' shells do not keep environment variables between commands. Also have it silence the page snapshot the CLI prints after every command (`PLAYWRIGHT_MCP_SNAPSHOT_MODE=none` and `--raw` worked in a trial), and take a snapshot only where a step needs one. Let it take the session name as an argument or variable so a feature that simulates several users or devices gets one session each. Target elements with role locators such as `"getByRole('button', { name: 'Save' })"`. Check which browser the pinned version expects. If it falls back to a system browser, say so in the skill. The CLI also keeps session files outside the repo (under `~/.cache/ms-playwright/` and `/tmp`), so Cleanup must close the sessions it opened. If the project has no Playwright, add it as a pinned dev dependency, or use a pinned `npx playwright@<version>` when the repo forbids new dependencies.

  Sign-in: use a run-owned test account or a saved browser session under `.cache/` (Playwright `storageState`, loaded with `pw.sh state-load <file>`). Never use the developer's session or a real third-party account. If a login cannot be automated (MFA, captcha), stub it at an existing production boundary, such as a configurable auth issuer URL. Reading the dependency's source to find that boundary is fine. If there is none, mark the dependent steps `blocked` and give the reason.

  One agent owns all driving. Source readers never drive. Every wait on startup, a command or an asynchronous operation has an observable result and a finite deadline: the expected duration plus a margin. Run long operations (about five minutes or more) in the background or with bounded polling and progress updates. Five minutes is not an execution limit. Bound each poll so a hung request cannot defeat the deadline. On timeout, capture diagnostics, report the unmet condition and run Cleanup. Put the real deadlines in the helpers and recipes, not arbitrary sleeps. For time-dependent behavior, shift the clock of the process the run owns. Never edit stored data to fake time.
- **When a drive fails.** Copy from `drive-failures.md`.
- **Evidence.** Everything a run writes goes under `.agents/skills/verify-<app>/.cache/`, which is gitignored: the same path in every project. Only a tool's own session files may live elsewhere, and Cleanup removes them. Proof for a feature goes to `.cache/evidence/<feature>/`. Proof standards: exercise the real user path, not internal setters or test-only endpoints. Capture the action and the resulting state, not just the final screen. Verify side effects (files written, rows inserted, messages sent) next to what is visible. Mock only where a production boundary already isolates the external system. For a dry run or test mode, observe what it actually skips instead of trusting its name.
- **Report.** One line per feature: **pass** (all mapped checks exercised and met), **fail** (an exercised check missed), **partial** (some checks exercised without failures, others unverified) or **blocked** (no meaningful drive after trying to create the prerequisite). A known failure stays failed. List checks not exercised. For a blocked path, give the missing prerequisite and what was tried. Link evidence with Markdown links to absolute paths from the current checkout, for example `trash — fail at "empty to trash" — [empty.png](/abs/checkout/.agents/skills/verify-app/.cache/evidence/trash/empty.png)`. Check every linked file exists after cleanup. A UI failure gets a screenshot. Other surfaces get request and response or terminal output. Report cleanup failures separately: a passing feature does not mean cleanup succeeded. For `shared`, add the lower-confidence label.
- **Cleanup.** The exact commands from the lifecycle rules, for completion, failure and interruption. Stop only recorded processes. Remove run-owned resources and temporary state. Keep proof and the diagnostic logs the report needs. Check that the original environment is restored and linked evidence survives. If cleanup fails, keep the ownership record and say what remains.
- **Helpers.** Every script in `bin/`, what it does and how to call it. Scripts are bash and executable. They may call other runtimes the project already needs, such as `node`. Windows developers run their agent inside WSL.
